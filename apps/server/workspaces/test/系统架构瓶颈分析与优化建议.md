# 系统架构瓶颈分析与优化建议

> 分析对象：`会话管理功能-PRD.md`（v1.0）中定义的会话管理系统架构
> 分析范围：数据模型、索引设计、分页方案、过期清理策略、软删除机制、配置与可靠性
> 说明：当前工作区仅有 PRD 文档，尚未有可访问的实现代码。本分析基于 PRD 描述的架构进行推演，重点找出会导致瓶颈、数据一致性风险、扩展性受限的设计点。

---

## 一、总体结论

PRD 定义的是一个基于 **SQLite 单库单表** 的会话管理系统。该方案在小规模（≤100 万条、单进程）场景下基本可用，但存在 **5 个核心架构瓶颈**，会在并发写入、深分页、批量清理、多租户隔离、水平扩展等场景下显著退化：

| # | 瓶颈 | 严重度 | 影响 |
|---|------|--------|------|
| B1 | 单机 SQLite 写入串行化 + WAL 单一写者 | 高 | 并发创建/更新吞吐受限，水平扩展困难 |
| B2 | `deleted_at` 导致索引失效与查询计划劣化 | 高 | 大数据量分页查询超时 |
| B3 | 计 `total` 触发的 `COUNT(*)` 全表扫描 | 中 | 默认查询路径 P99 超标 |
| B4 | 背景清理任务与在线查询读写冲突 | 中 | 主业务被清理任务拖慢 / 锁竞争 |
| B5 | 数据模型缺少访问隔离与租户维度 | 高 | 鉴权无法落到数据库层，无法多租户 |
| B6 | 配置缺省值集中在常数、无热更新 | 低~中 | 运维扩展性受限 |

## 二、逐项瓶颈分析

### B1. 单机 SQLite：写入串行化与扩展性天花板

**现状（PRD 5.2 / FR1 / 可靠性要求）**

- 使用 SQLite 持久化，开启 WAL。
- 目标是 “创建成功率 ≥ 99.9%” 与 “持久化不丢失”。
- `id` 为自增主键，`session_id` 加唯一索引。

**瓶颈点**

1. **单一写者（Single Writer）**：SQLite 同一时刻只允许一个写入事务。WAL 只缓解“读-写”并发，不缓解“写-写”。所有 `INSERT / UPDATE`（创建、更新、软删、恢复）在被同一进程串行化排队。
2. **本地文件存储**：单机磁盘，无法水平横向扩展。并发会话创建量升高后，写入延迟跟随时长增长，P99 会随之上升。
3. **可靠性目标与 SQLite 不匹配**：PRD 提出 “持久化写入不丢失” 与 99.9% 成功率，但 SQLite 面向**单节点嵌入式**场景，无主从复制、无跨机容灾，一旦机器磁盘故障即整库丢失。这与“不丢失”目标存在架构性冲突。

**优化建议**

- **定位切换**：将“会话管理”当作**低延迟写入**型服务。若写入 QPS 预计 > 数百/s 或有强一致性 + 高可用要求，应迁移到 PostgreSQL（支持并行写入、流复制、在线备份、独立于主业务扩容）。
- **保留 SQLite 的兜底**：SQLite 适合单机工具、本地缓存或边缘节点。若确定维持 SQLite，务必：
  - 启用 `PRAGMA synchronous=FULL | NORMAL`（NORMAL + WAL 可保不丢，除非断电场景需 FULL）。
  - 单一写者应用层集中，避免多进程并发写同一个库文件。
- **写入批量合并**：将“创建会话 + 写入 payload + 更新元数据”合并为**一个事务**，减少提交次数。
- **引入“写入侧队列 + 异步落库”**（若允许最终一致）：创建接口先返回、后台批量刷盘。但需权衡“写入不丢失”诉求。

### B2. 软删除字段破坏索引 → 分页与过滤劣化

**现状（PRD 5.1 / 5.2）**

- `deleted_at TEXT NULL` 表示软删除；默认查询过滤 `deleted_at IS NULL`。
- 建了 3 个单列索引：`created_at`、`expires_at`、`deleted_at`。

**瓶颈点**

1. **`IS NULL` 条件 + 非稀疏 WHERE**：`deleted_at IS NULL` 命中大多数行，优化器往往放弃走 `idx_sessions_deleted_at`（选择性太低），转而对 `created_at` 或主键做过滤+排序，扫描大量非删除行再丢弃。
2. **单列 `created_at` 索引无法支撑 “按时间倒序 + 分页 + 过滤未删除” 组合**：需要 `(created_at) DESC` + 过滤条件联合，单列索引需要在过滤后再排序，产生临时表排序。
3. **软删与物理删并存**：大量软删行堆积，主键/unique 索引膨胀，占用空间、拖慢插入维护。

**优化建议**

- **改为复合索引 / 部分索引（Partial Index）**，如 SQLite / PG 均支持：
  ```sql
  -- PG: 部分索引，仅索引“未删除且在有效期”的行，体积小、命中率高
  CREATE INDEX idx_sessions_active
      ON sessions (created_at DESC)
      WHERE deleted_at IS NULL;
  ```
  SQLite（≥3.8）同样支持部分索引。这样普通查询直接命中“活跃会话”索引，排序无需回表。
- **查询必须带上 user_id/user 租户维度**（见 B5），让索引更高选择性。
- **考虑“归档 + 定期硬删”**：软删行超过 `HARD_DELETE` 阈值/保留期后，批量物理删除或将 `deleted_at IS NOT NULL` 的行迁移到 `sessions_archive` 冷表，保持主表瘦身。

### B3. `COUNT(*)` 统计 total 拖慢默认查询

**现状（PRD FR3）**

- “可返回 `total` 总数（供前端分页控件使用）”，即分页接口带 `COUNT(*)`。

**瓶颈点**

- 每次分页都执行一次 `SELECT COUNT(*) FROM sessions WHERE deleted_at IS NULL ...`，在 100 万行 + 软删过滤 + 租户过滤的组合下，`COUNT(*)` 常退化为全表/全索引扫描，耗时远超“分页查询 P99 < 100ms”的目标。数据量越大越明显。

**优化建议**

- **默认不返回 total**，仅返回 `has_next / next_cursor`（游标分页天然支持）。
- 需要 total 的场景：改为 **近似计数** 或 **异步/缓存计数**（单独后台任务维护一个 `count` 计数器，或使用 SQLite/SQLite外统计），避免在主查询路径上做全量 count。
- 分页主路径用 **游标分页**（目标 PRD 已推荐），用 `WHERE (created_at, session_id) < (?, ?) ORDER BY created_at DESC LIMIT n` 走联合索引，替代 `OFFSET` 深翻页。

### B4. 定时清理任务与在线读写竞争

**现状（FR4）**

- 两种策略：惰性清理（查询过滤 `expires_at < now`）+ 后台定时任务批量删除。
- `CLEANUP_CRON = 0 3 * * *`，每日凌晨全表扫过期。

**瓶颈点**

1. **定时任务全表扫描**：无状态地 `DELETE ... WHERE expires_at < now` 会扫到 `expires_at` 索引，但若过期行量大，一次提交占用大量写锁/写事务，在 SQLite 单写下会 **阻塞在线创建/删除数秒到数分钟**。
2. **事务过大**：一次性删除几万~几十万行，WAL 变大、锁持有时间长，与“创建 P99 < 50ms”冲突。
3. **清理时机单一**：只有每日一次，过期但未清理的行在查询中被过滤（惰性），但物理空间不释放，存储缓慢膨胀——与 PRD 背景“防止存储膨胀”目标相悖。

**优化建议**

- **批量化 + 限流**：清理任务以固定批次（如每批 1 000 行）+ `LIMIT` + 短暂 sleep 提交，避免长事务持锁。
- **清理索引设计**：用 `(expires_at, deleted_at)` 或部分索引 `WHERE deleted_at IS NULL AND expires_at < now`，让清理任务快速定位。
- **自调节调度**：不只每日一次，可配置频率（每 N 分钟），配合“距当前过期超过保留期的行才删”，避免删到刚过期仍可能被恢复的场景（若需保留，改为软删/归档）。
- **清理与主业务的资源隔离**：在 SQLite 「单写者」约束下，把清理窗口放到低峰期；或改用 PG 后清理任务可在独立连接/分支运行，降低对主写路径的干扰。

### B5. 缺乏租户/用户访问隔离（多租户瓶颈）

**现状（FR 安全性 / 数据模型）**

- 表有 `user_id`（可空），但 `user_id` **没有索引**，且 PRD 把“按 user_id 做访问隔离（多租户）”列为待定问题（Open Question 1）。
- 安全性要求“未经授权的用户不可访问他人会话”，但只在查询层/中间件层约束。

**瓶颈点**

1. 没有按 `user_id` 建索引 → “查某用户会话”会走 `created_at` 索引后全量过滤，越多用户越慢。
2. 无数据库层强制隔离，只能依赖应用层 WHERE 拼接，易漏改导致**越权数据泄露**（安全高风险）。
3. 无法按租户做数据分区/归档/独立计费。

**优化建议**

- **将 `user_id` 设为查询默认维度**并建立复合索引（与 B2 合并）：
  ```sql
  CREATE INDEX idx_sessions_user_active ON sessions (user_id, created_at DESC) WHERE deleted_at IS NULL;
  ```
- **数据库层强制多租户**：所有查询条件强制带 `user_id`，关键写路径校验 `userId` 不得越权；必要时用 PostgreSQL **Row-Level Security（RLS）** 兜底。
- 明确 Open Question 1 的结论：若需多租户，`user_id` 必加索引并纳入所有查询与清理逻辑。

### B6. 配置集中性与热更新不足

**现状（第 6 节配置项）**

- `SESSION_TTL_DAYS / DB_PATH / DB_WAL_MODE / CLEANUP_CRON / HARD_DELETE_ENABLED`。
- 通过环境变量覆盖。

**瓶颈点**

- 纯环境变量配置无法**运行时热更新**；修改 `SESSION_TTL_DAYS` 或 `CLEANUP_CRON` 需重启服务，运维成本高。
- 缺少对 `session_id` UUID 生成、payload 大小上限、单用户会话数上限等防滥用配置。

**优化建议**

- 引入集中配置管理（如 env + 配置文件 + 运行时刷新），支持 `SESSION_TTL_DAYS`、`CLEANUP_CRON` 等热更新。
- 新增防滥用上限配置：每个 `user_id` 会话数上限、`payload` 大小上限、单次查询 `limit` 上限，防止一个用户打爆存储/查询资源。

## 三、优先级排序：建议的落地顺序

| 优先级 | 事项 | 对应瓶颈 | 预计收益 |
|--------|------|---------|---------|
| P0 | 数据模型增加 `user_id` 复合/部分索引，改部分索引 (`deleted_at IS NULL`) | B2, B5 | 分页与过滤不再退化，基线性能达标 |
| P0 | 分页默认去掉 `COUNT(*)`，用游标 + `has_next` | B3 | 默认查询路径 P99 稳定 < 100ms |
| P1 | 清理任务改为“分批 + 限流 + 低峰窗口 + 部分索引” | B4 | 消除清理对在线写入的阻塞 |
| P1 | 明确多租户，`user_id` 纳入所有查询、索引、RLS | B5 | 安全 + 性能双提升 |
| P2 | 评估 SQLite → PostgreSQL 的演进路径（写入吞吐/高可用） | B1 | 支撑更大规模与可靠性目标 |
| P2 | 软删定期归档/硬删，控制主表体积 | B2 | 防止存储无限膨胀 |

## 四、量化验收建议（针对 PRD §8 验收项）

现有验收“100 万条时，分页查询 P99 < 100ms”需补充**压力场景定义**，否则无法复现：

1. 必须明确**过滤条件组合**（是否带 `user_id`、是否过滤 `deleted_at`、是否计算 total）。
2. 必须明确**数据分布**（活跃/软删比、每用户会话数）。
3. 必须明确**并发创建、并发查询、清理任务同时运行**时的延迟，而不是单请求延时（这才是真正的性能瓶颈所在）。
4. 建议补充“清理任务运行期间，创建 P99、查询 P99 是否仍达标”的用例（对应 B4）。
5. 建议补充“同一用户查自己的会话 + 越权访问他人会话”的鉴权测试（对应 B5）。

## 五、总结

- 当前 PRD 定义的 SQLite 单表方案，在 **并发写吞吐、深分页、软删过滤、批量清理、多租户隔离** 五个维度存在明确瓶颈。
- **最小改动、立即可行的优化**是：① 改成“活跃行”部分索引/复合索引；② 分页去掉 `COUNT(*)`、走游标；③ 清理任务分批限流。这三项即可让 PRD 的核心性能指标达标。
- **架构级升级**（SQLite → PostgreSQL / 分布式存储、RLS 多租户、读写与清理分离）应作为第二阶段演进，匹配“持久化不丢失、高可用、可水平扩展”的目标。
