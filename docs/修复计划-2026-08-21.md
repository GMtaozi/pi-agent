## 三、重复项处理方案

### 3.1 高优先级：`packages/capabilities` 与 `packages/tools` 合并

**现状**
- `packages/capabilities` 定义了 `CapabilityRegistry` 和 8 个 Capability 类，但 `read/write/edit/generate-image` 的 `execute()` 全是 TODO/stub。
- `packages/tools` 已有完整实现：`ReadFileTool`、`WriteFileTool`、`EditFileTool`、`GenerateImageTool` 等。
- `apps/server/src/index.ts` 和 `packages/agent-engine/src/engine.ts` 实际使用的是 `packages/tools`，**`packages/capabilities` 完全未被业务引用**。

**建议方案 A（推荐）**：直接删除 `packages/capabilities`
- 理由：该包自始至终未接入业务，且已有完整的 `packages/tools` 替代。
- 操作：
  1. 删除 `packages/capabilities` 目录
  2. 删除 `pnpm-workspace.yaml` 中相关引用
  3. 删除 `apps/server/src/index.ts` 中的 `CapabilityRegistry` import
  4. 删除 `apps/server/src/__tests__/mocks.ts` 中的 `MockCapabilityRegistry`
  5. 删除 `apps/server/src/__tests__/integration.test.ts` 中的 capabilities 相关测试
  6. 运行 `pnpm check` 和 `pnpm test` 验证

**建议方案 B（保守）**：保留 `packages/capabilities` 作为兼容层，但标记为 deprecated
- `CapabilityRegistry` 委托给 `packages/tools` 的 `ToolRegistry`
- 在文档中标注 deprecated，给下游迁移时间

**推荐选择**：方案 A（删除）。理由：当前项目处于 Phase 0 早期，无外部依赖方，直接删除可避免长期维护双轨。

### 3.2 中优先级：日志实现重复

**现状**
- `packages/logging` 是真实实现。
- `agent-orchestrator/src/types/logging.ts` 和 `workflow/src/types/logging.ts` 各有一份完全相同的副本。

**建议**
1. 删除 `agent-orchestrator/src/types/logging.ts`
2. 删除 `workflow/src/types/logging.ts`
3. 在两个包中统一 `import { Logger } from '@workforge/logging'`
4. 检查是否有其他包有类似重复

### 3.3 P2 重复项

**前端配置逻辑重复**
- `SettingsPage`、`ModelsSettings`、`ModelSelect` 职责交叉。
- 建议收拢为单一 Settings 流程，明确分工。

```ts

// server
agentEngine.onStreamEvent(id, {
  onEvent: (event) => sendEvent('agent_event', { event }),
  onComplete: (response) => sendEvent('done', { response }),

});

// 需要确保 agentEngine.stream() 真的在产出事件
```

**验证**
