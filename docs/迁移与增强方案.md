# Pi-Console → WorkForge 迁移与增强方案

> **文档版本**：v1.0  
> **创建日期**：2026-09-02  
> **目标**：将 Pi-Console 的监控和调试能力迁移到 WorkForge，放弃拖拽编辑器，强化对话式 Agent 生成器定位  

---

## 一、项目空间决策

### 1.1 是否需要迁移？

**结论：不需要物理迁移项目空间，采用"增强 WorkForge"策略**

| 方案 | 操作 | 优劣 |
|------|------|------|
| **A. 物理迁移** | 将 Pi-Console 代码复制到 WorkForge | 代码冲突多，WorkForge 已有运行中的 Phase 0 产品 |
| **B. 增强 WorkForge**（推荐） | 在 WorkForge 中新增 Pi-Console 的监控模块 | 保留 WorkForge 架构优势，渐进式增强 |
| **C. 并行开发** | 两个项目独立，通过 API 集成 | 维护成本高，用户体验割裂 |

**推荐方案 B**：WorkForge 架构更先进（Monorepo + Agent 引擎 + Skills），Pi-Console 的拖拽编辑器已过时，只需将其**监控和调试能力**作为模块嵌入 WorkForge。

## 二、能力映射：Pi-Console → WorkForge

### 2.1 需要迁移的能力

| Pi-Console 模块 | WorkForge 对应模块 | 迁移方式 | 优先级 |
|-----------------|-------------------|----------|--------|
| 执行监控面板 | `packages/monitoring` | 增强现有模块 | P0 |
| 节点执行日志 | `packages/logging` | 增强现有模块 | P0 |
| Token 消耗追踪 | `packages/monitoring` | 新增功能 | P0 |
| 成本分析仪表盘 | `packages/monitoring` | 新增功能 | P1 |
| 断点调试 | `packages/agent-engine` | 新增功能 | P1 |
| 执行历史回放 | `packages/persistence` | 新增功能 | P1 |
| 流式输出 | `apps/web` | 已有，需优化 | P0 |
| 对话界面 | `apps/web` | 已有，需优化 | P0 |

### 2.2 不需要迁移的能力

| Pi-Console 模块 | 原因 |
|-----------------|------|
| 拖拽工作流编辑器 | 交互范式过时，WorkForge 用对话式 |
| DAG 引擎 | WorkForge 的 Agent 引擎更先进 |
| 节点类型体系 | WorkForge 用 Skills 替代 |
| 变量解析器 | WorkForge 的 Agent 引擎内置 |
| 条件分支节点 | 由 Agent 自主决策 |
| 并行执行节点 | 由 Agent 自主决策 |

```sql
CREATE TABLE IF NOT EXISTS monitoring_executions (
  id TEXT PRIMARY KEY,
  agent_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'running',
  started_at TEXT NOT NULL,
  completed_at TEXT,
  total_tokens INTEGER DEFAULT 0,
```

```sql
CREATE TABLE IF NOT EXISTS monitoring_node_logs (
  id TEXT PRIMARY KEY,

  node_type TEXT,

  started_at TEXT NOT NULL,
  completed_at TEXT,
```
