## 0. 文档目的与适用范围

本文档为 pi-agent 进入**商业化阶段**提供一套可落地、可度量、可决策的数据体系。当前平台已具备**执行监控、成本分析、Token 追踪**三大基础能力，本文在此基础上补齐**用户行为、产品指标、业务指标**三块，形成"技术运营 → 产品体验 → 商业结果"的完整度量闭环。

**度量层级（自上而下）**

```
商业结果层（赚不赚钱）  → 业务指标体系（MRR/ARR/LTV/CAC/流失）
       ↑
产品价值层（用得好不好）→ 产品指标体系（北极星/一二级指标）
       ↑
用户行为层（怎么用）    → 用户行为分析（旅程/漏斗/留存）
       ↑
技术运营层（稳不稳）    → 已有：执行监控/成本分析/Token 追踪
```

**数据来源基线**
- 埋点事件（前端/服务端统一事件总线）
- 已有监控数据：执行次数、Token 消耗、成本、耗时、模型占比、成功率
- 业务系统：租户（tenant）、用户（user）、订阅（subscription）、订单（billing）
- 外部：竞品功能矩阵对标（季度）、用户调研 NPS/契合度

## 1. 产品指标体系

### 1.1 北极星指标（North Star Metric）

> **北极星指标 = 每周活跃生产型 Agent 执行的"有效对话/任务"次数（Weekly Active Agent Executions, WAAE）**

定义拆解：
- **Agent**：已创建且被用户成功配置（非草稿）的 Agent
- **生产型**：近 30 天内有 ≥ 1 次真实调用（排除仅测试）
- **有效执行**：返回结果且未被用户手动终止、且调用了至少 1 次 LLM/工具节点
- **周维度**：滚动 7 天去重后汇总

**为什么选它**：它同时承载了"用户规模（Agent 数）× 使用深度（执行频率）× 价值交付（有效）"三重含义，且与平台已有的 Token/成本数据天然打通。相比单纯的"注册用户数"或"Agent 创建数"，WAAE 能真实反映平台是否创造了使用价值，是商业收入的最终上游。

**与路线图北极星对齐**：路线图中的"月活跃企业租户"是 WAAE 的**租户聚合视角**，二者可互相校验（活跃租户 = 含 ≥ 1 个生产型 Agent 且 WAAE > 0 的租户）。

### 1.2 一级指标（4 个支柱，对齐路线图三大支柱）

| 一级指标 | 定义 | 计算口径 | 当前基线 | M3 目标 | M6 目标 |
|---|---|---|---|---|---|
| **激活率（Activation）** | 新注册用户 7 日内创建 ≥ 1 个可用 Agent 并完成首轮有效对话 | 激活用户 / 新注册用户 | 待埋点基线 | 45% | 60% |
| **活跃度（Engagement）** | 周活跃租户（WAU-Tenant）与 WAAE | 见 1.1 | 1.0×（基线期） | 2.5× | 5× |
| **留存率（Retention）** | 租户次周/次月留存（见 §2.3） | 留存租户 / 同期新增租户 | 待基线 | 周留存 60% | 月留存 70% |
| **变现率（Monetization）** | 付费租户 / 活跃租户 | 付费转化 | 0% | 内测 5% | 公测 12% |

### 1.3 二级指标（按支柱分解，可直接落到看板）

**激活类**
- 首 Agent 创建耗时（P50/P90）— 当前已测 30 秒生成配置，目标 P90 < 60s
- 自然语言创建成功率（生成配置后用户保存比例）
- 模板创建渗透率（经模板创建的 Agent / 总创建）
- 知识库绑定率（创建 Agent 后绑定知识库比例）

**活跃类**
- 人均周执行次数（WAUE per user）
- 工作流编排渗透率（使用可视化编排的租户占比）— 路线图 M3 重点
- 多 Agent 协作使用率
- 插件/MCP 调用量 — 路线图 M3 生态指标
- 调试面板周活（DevOps/开发者）
- 知识库检索调用频次（RAG 使用深度）

**留存类**
- 新租户 1/2/4/8 周留存曲线
- 功能采用阶梯（注册 → 创建 → 对话 → 编排 → 部署 → 付费）
- 沉默预警：连续 14 天 0 执行的活跃租户数

**质量/体验类**
- 对话首响时间（TTFT, Time To First Token）P50/P95
- 执行成功率（成功 / 总执行，已有监控）
- RAG 检索准确率（评测集，已有规划）
- 告警误报率（已有 NotificationService）
- 非技术用户契合度（季度复测，当前 68–72%，目标 88%）
- NPS（季度）

**商业化支撑类（与 §3 联动）**
- 活跃租户数、付费租户数、ARPA（每租户平均收入）
- 单租户成本（Token+算力，已有成本分析可分摊）
- 网关降本比例（M5 AI 网关路由节省）

## 2. 用户行为分析

### 2.1 用户旅程地图（五类角色 × 核心阶段）

以**企业开发者**与**内容创作者**两条主线为例，映射埋点事件：

```
[认知] → [注册登录] → [上手激活] → [深度使用] → [价值固化] → [付费/扩散]
   │          │            │            │            │           │
 落地页     TC-001      首 Agent     工作流/    知识库沉淀   订阅套餐
 来源追踪   首登成功     TC-002~007  知识库     多Agent协作  邀请成员
                         TC-012团队
```

| 阶段 | 关键事件（Event） | 关注点 |
|---|---|---|
| 认知/获取 | `page_view`, `signup_start`, `signup_success` | 渠道转化、来源质量 |
| 上手激活 | `agent_create`, `agent_first_chat`, `kb_create`, `template_use` | 激活漏斗（§2.2） |
| 深度使用 | `workflow_run`, `kb_search`, `debug_open`, `mcp_call` | 功能采用、粘性 |
| 价值固化 | `agent_publish`, `deploy_docker`, `api_key_create` | 生产化、留存前置 |
| 付费/扩散 | `subscription_start`, `invite_member`, `share_agent` | 变现、口碑 |

### 2.2 漏斗分析（Funnel）

**核心转化漏斗（全平台）**

| 步骤 | 漏斗环节 | 流失监控阈值 |
|---|---|---|
| 1 | 注册成功 | — |
| 2 | 完成首个 Agent 创建 | 步骤1→2 转化率 < 50% 预警 |
| 3 | 完成首轮有效对话（≥3 轮） | 步骤2→3 < 70% 预警 |
| 4 | 7 日内回访（激活） | 步骤3→4 < 45% 预警 |
| 5 | 30 日内生产化（部署/API/发布） | 步骤4→5 重点增长杠杆 |
| 6 | 付费转化 | 对应 §3 变现率 |

**角色分层漏斗**
- 内容创作者：模板创建 → 知识库上传 → 对话 → 周留存（重点降门槛）
- 企业开发者：API Key 创建 → 工作流编排 → 部署 → 团队邀请（重点提深度）
- DevOps：监控面板 → 告警配置 → 一键部署（重点提稳定性感知）

**分析方法**：按渠道、按注册周（cohort）、按角色做分层漏斗；定位最大单步流失并归因（产品缺陷 / 引导缺失 / 需求错配）。

### 2.3 留存分析（Retention）

**留存定义**
- 租户留存：以租户注册周为 cohort，观察其后每周是否有 WAAE > 0
- 用户留存：以用户首次激活周为 cohort，观察后续周活跃

**留存矩阵（Cohort Retention，示例结构）**

| 注册周 | 第1周 | 第2周 | 第4周 | 第8周 |
|---|---|---|---|---|
| W1 | 100% | 62% | 48% | 35% |
| W2 | 100% | 65% | — | — |

**关键留存指标**
- 次日/7日/30日租户留存
- 经典 SaaS "魔法数字"：找到"在首周完成 ≥ 3 次有效执行"的用户留存是否显著高于均值（验证激活标准合理性）
- 流失预警分：基于"执行频次衰减 + 功能使用收窄"构建沉默评分，提前 14 天预警

**留存驱动因素拆解**：对比高留存租户 vs 流失租户在"知识库绑定 / 工作流使用 / 团队规模"上的差异，反哺产品优先级。

## 3. 业务指标体系（商业化核心）

> 假设 pi-agent 采用 **租户（企业）订阅 + 用量（Token/执行）混合计费**（路线图 M4 商业化）。以下指标以"租户"为计费单元。

### 3.1 核心指标定义与公式

| 指标 | 定义 | 公式 | 说明 |
|---|---|---|---|
| **MRR** 月度经常性收入 | 当月所有订阅+用量保底的标准化月收入 | Σ(活跃订阅月费) + 用量包月费 | 剔除一次性收入 |
| **ARR** 年度经常性收入 | MRR 年化 | MRR × 12 | 对外估值口径 |
| **ARPA** 每租户平均收入 | 收入集中度 | MRR / 活跃付费租户数 | 监测大客户依赖 |
| **LTV** 客户生命周期价值 | 单租户终身贡献 | ARPA × 毛利率% / 月流失率 | 需留存率支撑 |
| **CAC** 客户获取成本 | 获取一个付费租户成本 | 总获客费用 / 新增付费租户数 | 含市场+销售+返佣 |
| **LTV/CAC** | 单位获客回报 | LTV / CAC | **健康线 ≥ 3** |
| **付费转化率** | 活跃→付费 | 付费租户 / 活跃租户 | 目标 M3 5% / M6 12% |
| **流失率（Churn）** | 月流失 | 当月流失租户 MRR / 期初 MRR | 含主动取消+沉默失效 |
| **净收入留存 NRR** | 扩张能力 | (期初MRR+增购−降级−流失)/期初MRR | **>100% 为优** |
| **回收期** | 回本周期 | CAC / (ARPA × 毛利率)（月） | 越短越好，目标 < 12 月 |

### 3.2 指标联动关系（单位经济模型）

```
CAC ─────────────┐
                  ├─→ LTV/CAC ≥ 3（获客健康）
LTV = ARPA×毛利/流失率 ─┘
                  ↘→ NRR > 100%（扩张健康，降低对新增依赖）
MRR 增长 = 新增 MRR + 扩张 MRR − 流失 MRR − 降级 MRR
```

**预警规则示例**
- LTV/CAC < 3 → 获客效率告警
- 月流失率 > 5% → 留存告警（联动 §2.3 预警分）
- NRR < 100% → 增购/降价策略审查
- ARPA 集中度（Top3 租户占比 > 50%）→ 大客户风险

### 3.3 数据口径与采集点
- 订阅状态、套餐档位、用量包：`billing/subscription` 表（M4 新增）
- 获客费用：市场渠道花费台账（需人工/财务录入，建议建轻量成本归集表）
- Token/执行成本分摊：复用现有成本分析模块，按租户归集（M1 成本分摊已规划）

### 4.4 看板建设原则
- **单一事实源**：所有指标口径以本文为准，避免同名不同义

- **阈值可视化**：目标线、预警线直接画在图表上
- **自动化**：日报/周报定时生成推送，减少人工

## 5. 数据质量评估

> 没有可信的数据，指标就是噪音。本节定义对"事件埋点 + 业务数据"的质量门禁。

### 5.1 三维质量模型

| 维度 | 定义 | 评估方法 | 合格线 |
|---|---|---|---|
| **完整性 Completeness** | 应采集事件无丢失 | 1−(缺失事件数/应采集数)；关键字段空值率 | ≥ 99.5% |
| **准确性 Accuracy** | 数值与真实一致 | 抽样对账（埋点 vs 后端日志 vs 财务）；ID 去重率 | 偏差 < 1% |
| **及时性 Timeliness** | 数据可用延迟 | 事件产生 → 入仓可查 时延（P95）；日报准时率 | 时延 P95 < 5min |

### 5.2 质量监控机制
- **完整性**：对每个关键事件设"预期量级基线"，偏离 ±30% 自动告警（防埋点丢失）
- **准确性**：每日抽样 100 条事件与后端 `execution` 日志对账；MRR 与财务月结对账（月度）
- **及时性**：数据管道 SLA 监控，入仓延迟超阈值告警
- **一致性**：建立指标字典（metric registry），同名指标全局唯一口径，变更需评审

### 5.3 数据质量看板（建议纳入实时监控）
- 各事件采集量 + 偏离度
- 空值字段 Top
- 管道延迟 P50/P95
- 指标字典版本与变更记录

## 6. A/B 测试框架

> 用于验证产品改动（如新引导流程、模板推荐算法、定价页）是否真带来指标提升，避免"拍脑袋决策"。

### 6.1 实验生命周期

```
假设提出 → 指标定义 → 实验设计 → 流量分配 → 运行观测 → 显著性检验 → 决策 → 归档
```

### 6.2 实验设计要点

| 要素 | 规范 |
|---|---|
| **假设** | 必须为可证伪陈述，如"新引导页使激活率从 40% → 48%" |
| **主指标（OEC）** | 每次实验唯一主指标，优先北极星相关（激活率/WAAE） |
| **护栏指标** | 必须监控：执行成功率、TTFT、成本，防主指标提升但体验受损 |
| **样本量** | 基于主指标基线、最小可检测效应（MDE=5%）、α=0.05、power=0.8 计算 |
| **分组** | 随机分桶（用户/租户级，避免同一租户命中多组）；默认 50/50，可 90/10 小流量起 |
| **运行周期** | ≥ 1 个完整周（覆盖周内波动）；重大改动 ≥ 2 周 |
| **防作弊** | 排除内部账号、机器人流量；新奇效应（novelty）观察需延长 |

### 6.3 统计显著性

- **检验方法**：主指标为比率 → 双比例 Z 检验；为均值 → Welch t 检验
- **显著性水平**：α = 0.05（95% 置信）；报告 p-value 与置信区间，**不只报"显著/不显著"**
- **多重比较**：多组对比用 Bonferroni / BH 校正，防假阳性
- **提前停止**：用序贯检验（如 alpha 消耗函数），不盲目每天看 p 值提前停
- **最小样本**：未达样本量前不解读结果

### 6.4 决策流程

```
            ┌─ p ≥ 0.05 且无业务意义 → 不采纳，归档学习
结果解读 ───┤
            ├─ p < 0.05 且护栏指标无恶化 → 采纳，全量发布
            └─ p < 0.05 但护栏恶化 → 不采纳/迭代（如限场景发布）
                    │
            ┌───────┴───────┐
        显著负向/无差异    显著正向
         → 回滚/放弃        → 全量 + 监控 2 周 + 更新指标基线
```

**决策原则**
- 主指标不显著但护栏恶化 → 坚决不发布
- 小流量（10%）已显著正向且护栏安全 → 可渐进全量，不必等满周期
- 所有实验结论（含失败）写入实验仓库，形成组织记忆
- 与路线图联动：M1 的 Prompt A/B 工具（roadmap 已规划）可直接复用本框架
