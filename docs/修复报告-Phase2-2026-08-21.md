## 四、遗留项与后续建议

### 4.1 立即遗留项（Phase 2 待完成）

1. **删除 packages/capabilities（t1）**
   - 风险：`integration.test.ts` 中可能有 capabilities 相关测试，删除后需清理
   - 回退方案：若测试失败，保留为 deprecated 兼容层

2. **删除重复 logging.ts（t2）**
   - 需在两个包的 `package.json` 中添加 `@workforge/logging` 依赖
   - 统一 `import { Logger } from '@workforge/logging'`
   - 需确认无其他包存在类似重复

3. **密钥加密文档对齐（t3）**
   - 更新 `docs/04-实施任务拆解与里程碑.md` T4.3 描述
   - 更新 `docs/Phase0-验收测试与加密存储报告.md`
   - 明确：实际使用 AES-256-GCM，DPAPI 未实现

4. **前端配置逻辑收拢（t4）**
   - SettingsPage.tsx 中仍有 ~40 行重复的 fetchSettings/fetchModels/updateTheme 逻辑
   - 建议：完全切换到 `useSettingsApi` hook，移除 SettingsPage 中的内联逻辑
   - ModelSelect 可进一步抽离为 ModelsSettings 的子组件

### 4.2 后续建议

1. **优先级排序**
   - 建议先完成 t1（删除 capabilities），减少认知负担
   - t2 紧随其后，清理重复代码
   - t3 文档对齐风险低，可与 t1/t2 并行
   - t4 前端收拢需要更多 UI 测试，最后完成

2. **验证策略**
   - 删除 packages/capabilities 后立即运行 `pnpm test`
   - 统一 logging 引用后运行 `pnpm check`
   - 考虑在 WSL/Docker 中解决 dev server EPERM，恢复前端验证

3. **长期建议**
   - 建立代码审计规则，防止新重复实现
   - 将 `packages/capabilities` 删除纳入 CI 检查，确保无人重新引入
   - 文档与代码一致性检查纳入 PR 流程
