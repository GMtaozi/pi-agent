## 问题 1：视频能力优先级 — H3 类 API 是否在 Phase 1 必须接入？

### 1.1 背景

产品核心卖点之一是"一句话产出视频"，竞品 Pi-mato 已演示视频产物。视频生成成本高、延迟大、质量波动明显，是 Phase 1 中最重的一块。需要决定：视频是否作为 Phase 1 的必须项，还是降级为可选项。

### 1.2 市场/能力现状（2026-08 调研）

- MiniMax H3：全模态生成模型，15 秒 / 2K 分辨率视频，官方报价约 0.8 元/秒，自称视频编辑榜单全球第一，且为首款开源多模态视频模型（权重开放，可本地部署）。
- 其余可选：Runway、Kling（可灵）、即梦、Veo、Step 视频等，均以 API 形式提供。
- 共同特征：按秒计费、生成耗时数十秒至分钟级、对提示词敏感（质量不稳定）。

### 1.3 候选方案对比

| 方案 | 内容 | 优点 | 缺点 | 成本/周期 |
|---|---|---|---|---|
| A. Phase 1 必接 | 视频 API 作为一等能力接入 | 卖点完整，demo 震撼 | 排期紧张，占 Phase 1 大头；质量不稳拉低整体体验 | 高 |
| B. Phase 1 预研+占位（推荐） | 视频能力做成脚手架 + 极简接入，仅接 1 家 API 打通链路 | 验证主链路（脚本-分镜-片段-拼接），风险可控；其余时间投入图片/语音 | 中；卖点演示受限 | 中 |
| C. Phase 2 再接入 | 先做好文本/图片/语音，视频延后 | 前期聚焦，质量可控 | 与竞品差异点后置，市场窗口可能错过 | 低 |

### 1.4 推荐决策

采用方案 B：Phase 1 做"视频组装管线"（脚本-分镜-片段生成-ffmpeg 拼接），接 MiniMax H3 一家打通端到端，其余视频 API 走统一适配接口预留。

理由：
1. 视频的护城河不在"调 API"，而在"编排"（分镜拆解、片段拼接、口播对齐）。组装管线与文本/图片/语音共用，先做管线、后填模型，是正确顺序。
2. H3 单价 0.8 元/秒，一次 15 秒视频约 12 元，成本敏感；先以"低频演示 + 预算审批"方式控制。
3. 若 Phase 1 全量做视频，图片/语音两个"高性价比卖点"会被挤掉。

### 1.5 影响与风险

- 架构影响：新增 VideoPipeline 模块（拆条、生成、拼接、对齐），独立于具体 API。
- 排期影响：Phase 1 中视频占 30-40% 工时。
- 风险：H3 API 可用性/限流不确定。回退：方案 C（延后），管线代码保留，接口不变。
- 已确认（2026-08-17）：视频口播/字幕对齐暂缓——产品以软件生态为主要目标，VideoPipeline 第一阶段不含对齐模块，后续按需追加。

## 问题 2：目标平台 — 仅 Web，还是需要桌面打包？

### 2.1 背景

MVP 设计为 Web（浏览器访问 127.0.0.1）。但产品是本地优先工具（本地文件工作台、本地密钥、本地记忆），浏览器有安全边界限制（沙箱、本地文件访问受限），且竞品多为桌面形态。需要确定打包形态。

### 2.2 候选方案对比

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| A. 纯 Web（本地服务） | 后端 Node 本地起服务，浏览器访问 | 开发快，前端技术栈自由 | 用户要开服务；本地文件/剪贴板/桌面集成受限；体验像"内网工具" |
| B. Web + Tauri 桌面壳（推荐） | 后端仍为本地 Node 服务，Tauri 壳包前端 | 体积小（约 10MB vs Electron 100MB+）、内存低、可调用系统能力（剪贴板/文件对话框/托盘）；前端代码几乎复用 | 需维护壳层；Windows 上 WebView2 依赖系统组件（Win10/11 自带） |
| C. Web + Electron 桌面壳 | Electron 打包 | 生态最成熟、能力最全 | 包大、内存高、升级频繁；对本地工具过重 |
| D. 双形态（Web + 桌面） | 同时支持 | 覆盖最广 | 双倍维护；MVP 阶段不必要 |

### 2.3 推荐决策

Phase 0/1 采用方案 A（纯 Web 本地服务，预留接口）；Phase 2 末尾升级方案 B（Tauri 壳）。

理由：
1. 架构上把"前端 UI"与"后端能力"分离，桌面壳只是前端的宿主，不影响后端与 Agent 引擎设计。
2. 纯 Web 先行，开发迭代最快；Tauri 迁移成本低（前端代码不变，加一层壳 + IPC）。
3. 密钥存储、剪贴板、文件对话框等系统能力在 Tauri 下更顺，但这不影响 Phase 0/1 的核心链路。

### 2.4 影响与风险

- 架构影响：前端必须走 HTTP/WebSocket 与后端通信（不依赖 Node 侧直接渲染），保证换壳不动逻辑。
- 密钥存储：Phase 0 用 AES-256-GCM 加密文件，Phase 2 如需系统级 keytar 可单独迁移。
- 风险：Tauri 在部分 Windows 环境 WebView2 缺失。回退：保持纯 Web 可用，桌面壳作为可选分发。
- 已确认（2026-08-17）：按推荐决策 Web 先行；托盘常驻/开机自启作为 Tauri 阶段增强项，非硬需求。

## 问题 3：Skills 生态 — 是否开放第三方发布？

### 3.1 背景

Skills（能力包）是本产品差异化的核心（Capability Cloud）。开放第三方发布可快速丰富生态，但也带来安全（恶意技能执行任意代码）、兼容性（格式演进）、运营（审核/分发）成本。

### 3.2 候选方案对比

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| A. 仅内置 + 本地目录（推荐 Phase 0-1） | Skills 只从本地目录加载（用户/工作台级），格式公开但不做分发渠道 | 零运营成本；安全边界清晰（本地可信目录）；聚焦核心体验 | 生态增长慢 |
| B. 开放 npm/git 安装 | 用户可用命令从 npm/git 安装 Skills 包 | 复用 Pi 的 packages 机制；生态可增长 | 需信任模型；依赖管理复杂；安全面扩大 |
| C. 开放商店/市场 | 中心化 Skills 市场，第三方提交 | 生态最繁荣 | 需审核、计费、账户体系；MVP 阶段过重 |

### 3.3 推荐决策

Phase 0-1：方案 A（本地目录加载，格式即"文档规范"）；Phase 2 视用户量决定是否升级方案 B（npm/git 安装，复用 Pi packages 机制）。商店（C）明确不做。

理由：
1. Skills 的核心价值先在于"用户可自己加技能"，第三方生态是锦上添花，不应在早期消耗排期。
2. 方案 B 可复用 Pi 已验证的包机制（npm/git + dependencies），升级路径平滑。
3. 安全：Skills 本质是代码，开放分发前必须设计信任模型（签名/来源标记/沙箱），这属于 Governance 范畴，Phase 2 一起做。

### 3.4 影响与风险

- 架构影响：Skills 加载器按目录扫描 + 元数据解析，格式稳定即可（不引入包管理依赖）。
- 安全影响：本地目录默认可信；若 Phase 2 开放安装，需加"来源标记 + 高危能力审批"。
- 风险：技能格式早期定错导致后续迁移成本。缓解：格式版本化（skills.json 带 version 字段）。
- 已确认（2026-08-17）：暂无必须支持的外部 Skills 来源，按推荐决策本地目录起步。

## 问题 4：记忆存储粒度 — 纯文件索引还是向量库？

### 4.1 背景

记忆需支持：跨会话注入偏好、按主题检索历史产物摘要。存储粒度决定检索质量、实现复杂度与依赖。

### 4.2 候选方案对比

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| A. JSON 文件 + 关键词索引（推荐 Phase 2 起步） | 记忆条目存 JSON，按标签/关键词/工作台过滤 | 零依赖、可读、可手工编辑、实现快 | 语义检索弱；条目多时全量扫描 |
| B. SQLite FTS5 全文检索 | 记忆入库，FTS5 索引 | 检索快、支持中文分词（需扩展）、单库 | 需建表/迁移；语义仍弱 |
| C. 向量库（sqlite-vec / 独立向量库） | 记忆向量化，相似度检索 | 语义检索强，可模糊召回相关记忆 | 需嵌入模型（额外 API/模型依赖）、索引维护、成本与延迟 |
| D. 混合（推荐最终态） | 结构化标签 + 语义向量 | 两者兼得 | 最复杂；分阶段引入 |

### 4.3 推荐决策

Phase 2 采用方案 A（JSON + 标签/关键词），上线后视检索质量升级：先到 B（FTS5，几乎零成本），若仍不足再引入 C（向量，选 sqlite-vec 这类本地嵌入式，避免独立向量库服务）。最终态 D。

理由：
1. 记忆条目的语义检索需求在早期并不高——偏好类记忆靠标签就够（"深色主题"对应 tag:preference），产物摘要靠"工作台 + 文件名"就够。
2. 向量化需要嵌入模型，引入额外 API 调用与成本，且记忆注入是每次会话都要跑的高频路径，过早向量化性价比低。
3. sqlite-vec 可做嵌入式（不引入服务），从 A 迁移到 D 时数据模型只需加一列向量，改动可控。

### 4.4 影响与风险

- 架构影响：MemoryService 接口抽象为"写入 + 按查询条件召回"，存储实现可替换（A/B/C/D 都是同一接口）。
- 成本影响：A/B 零新增成本；C 需嵌入模型（按 token 计费）。
- 风险：过早向量化带来维护负担；过晚则检索质量差。缓解：接口先抽象，阈值（如记忆条目超过 500 或召回不准反馈）作为升级触发条件。
- 已确认（2026-08-17）：暂不做跨工作台全局召回；若未来需要，再评估向量化。
