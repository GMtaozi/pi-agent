# 丝滑输出优化方案

> 目标：让 pi-agent 的对话输出达到 DSH / pi-agent / zocde 级别的“字字落盘”丝滑体验。  
> 日期：2026-08-21  
> 状态：规划中

---

## 一、当前状态

| 维度 | 现状 | 体验影响 |
|---|---|---|
| 前端 SSE 解析 | 已修复 `event.data` JSON.parse | 能收到输出 |
| 前端渲染频率 | 每个 token delta 都 `setMessages` | React 高频重渲染，掉帧 |
| Markdown 渲染 | 流式中持续跑 `ReactMarkdown + rehype-sanitize` | 单次渲染 10~30ms，卡顿 |
| 后端 SSE payload | 每次转发完整 `AgentMessage` | 带宽 & 解析开销大 |
| 滚动行为 | 强制滚到底 | 用户翻历史时被打断 |
| 光标 | 每次重渲染都重建 DOM | 闪烁、布局抖动 |

**结论**：功能已通，但“帧级体验”尚未优化。

---

## 二、优化方向（按优先级）

### P0：必须做（直接影响丝滑感）

#### 1. 前端 SSE 更新限流到 16ms
- **做法**：用 `requestAnimationFrame` 或 16ms `setTimeout` 合并多次 delta
- **效果**：React 重渲染从“每个 token”降到“每帧一次”，帧率从 30fps 提升到接近 60fps
- **文件**：`apps/web/src/pages/ChatPage.tsx`
- **参考**：
  ```tsx
  const scheduleAssistantFlush = (content: string) => {
    assistantContent = content;
    if (flushTimer) return;
    flushTimer = setTimeout(() => {
      flushTimer = undefined;
      setMessages(prev => {
        const updated = [...prev];
        updated[updated.length - 1] = { ...updated[updated.length - 1], content: assistantContent };
        return updated;
      });
    }, 16);
  };
  ```

#### 2. 流式过程中跳过 Markdown 解析
- **做法**：流式中用 `<span className="streaming-text">` 显示纯文本，结束后再切 `MarkdownRenderer`
- **效果**：单次渲染耗时从 10~30ms 降到接近 0ms
- **文件**：`apps/web/src/pages/ChatPage.tsx`、`apps/web/src/index.css`
- **注意**：保留 `white-space: pre-wrap`，保证换行和空格可读

#### 3. 后端 SSE payload 精简
- **做法**：在 `apps/server/src/index.ts` 的 SSE handler 中，只提取增量字段
  - `text_delta` → 发 `{ type: 'text_delta', delta: string }`
  - `thinking_delta` → 发 `{ type: 'thinking_delta', delta: string }`
  - `done` → 发完整最终 message
- **效果**：SSE payload 从几百字节降到几十字节，前端 JSON.parse 更快
- **文件**：`apps/server/src/index.ts`

---

### P1：强烈建议（接近 DSH 水准）

#### 4. 自动滚动优化
- **做法**：流式时判断用户是否在底部
  - 若在底部：`scrollIntoView({ behavior: 'smooth' })`
  - 若已上翻：不强制滚动，显示“新消息”按钮
- **效果**：用户翻历史时不会被强制打断
- **文件**：`apps/web/src/pages/ChatPage.tsx`

#### 5. React 重渲染范围收敛
- **做法**：
  - 消息列表用 `React.memo`，仅 `content/streaming` 变化的 assistant 消息才重渲染
  - 或把最后一条 assistant 消息拆成独立受控组件
- **效果**：消息列表越长，节省的 diff 成本越高
- **文件**：`apps/web/src/pages/ChatPage.tsx`

#### 6. 光标性能优化
- **做法**：把光标从 `<span className="cursor">▋</span>` 改成纯 CSS `::after` 伪元素
- **效果**：光标闪烁不受 React 重渲染影响
- **文件**：`apps/web/src/pages/ChatPage.tsx`、`apps/web/src/index.css`

---

### P2：锦上添花（长对话/复杂场景）

#### 7. 流式 Markdown（增量渲染）
- **做法**：对已闭合结构（代码块、列表、引用）做轻量解析，未闭合部分保持纯文本
- **效果**：流式中就能看到代码块高亮、列表序号，结束瞬间无格式跳变
- **复杂度**：高，建议在 P0/P1 完成后再评估

#### 8. 长对话虚拟滚动
- **做法**：引入 `react-window` 或 `react-virtualized`，只渲染可视区域消息
- **效果**：100+ 条消息时依然流畅
- **文件**：`apps/web/src/pages/ChatPage.tsx`

#### 9. 消息渲染 memoization
- **做法**：`MarkdownRenderer` 用 `React.memo` + 浅比较，避免相同内容重复解析
- **效果**：切换会话/重绘时减少不必要的 Markdown 解析
- **文件**：`apps/web/src/components/MarkdownRenderer.tsx`

## 四、验收标准

| 指标 | 当前（预估） | 目标 |
|---|---|---|
| 首 token 延迟 | < 500ms | < 300ms |
| 每帧渲染耗时 | 10~30ms | < 4ms |
| 流式更新频率 | 每个 token | ≤ 16ms/帧 |
| 滚动打断 | 总是强制滚底 | 仅底部时滚动 |
| 光标闪烁 | 有 | 无 |
| 100 条消息渲染 | 可能卡顿 | 保持 60fps |

## 五、风险与注意事项

| 风险 | 说明 | 规避 |
|---|---|---|
| 批量刷新导致“掉字” | 16ms 合并窗口内如果有 1~2 个 token 延迟，用户可能感知不到 | 实测调整到 16ms，不要太大 |
| Markdown 跳变 | 流式纯文本 → 结束 Markdown 的瞬间有视觉切换 | 可先做纯文本，确认性能后再评估是否需要流式 Markdown |
| 后端 SSE 改协议 | 精简 payload 后前端也要同步改解析逻辑 | 前后端一起改，一次提交 |
| 虚拟滚动复杂度 | 自动高度计算、滚动位置恢复 | 先做 P0/P1，再评估是否真的需要 |
